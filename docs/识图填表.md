# 识图填表（M4a/M4b）：图片附件、视觉直发、跨重启落盘

M4a 起，AI 助手可以接收测量记录表照片。入口是回形针、输入框 Ctrl+V 或从资源管理器拖放：选择 1–4 张 PNG / JPEG / WebP，图片先在本机校验、缩放、重编码，再按当前模型能力选择「直接看图」或「视觉备用模型先转写」。Work 模式下模型可以基于照片调用 M3 的读表/写表工具；Chat 模式只做图片问答，没有表格工具，联网搜索开启时可结合搜索结果。

M4b 起，**压缩后的发送图**会保存到本机附件目录，重启后仍能在查看器里打开原貌，也能直接重新生成；编辑用户消息时可以增删图片，新增图片先留在草稿托盘，保存或重发后才写入树与磁盘。`agent.json` 仍只保存缩略图与转写，不存 base64、路径或 `stored` 字段。

## 范围与入口

- 入口一：输入卡回形针 → 系统文件选择器，可多选。
- 入口二：焦点在输入框时按 Ctrl+V，从系统剪贴板取位图；截图工具与浏览器「复制图片」走这条。纯文字粘贴保持原样，不进入图片管线；同一剪贴板既有文字又有位图时以位图为准，并阻止默认粘贴，避免同一张截图既进草稿又粘出一段 HTML。从资源管理器复制图片文件能否粘贴，取决于 WebView 是否把系统文件剪贴板映射为 `File`；拿不到位图时不会有反应。
- 入口三：从资源管理器把 1–4 张图片文件拖到助手主区域（输入框草稿）或打开的编辑弹窗（编辑托盘）。只处理含 `Files` 的拖放，文字 / 选区拖放不受影响；拖入时显示「松开以添加图片」遮罩，离开、放下、窗口失焦或超时都会复位。设置或查看器打开、生成中、对话库只读、图片发送关闭时拒绝并说明原因；非图片文件逐个报错。
- 三个入口共用同一条校验、压缩、缩略图与发送确认管线，也共用 4 张上限与入口条件。
- **不支持应用内截图**（留待后续）。
- 格式：只认文件头，不信任扩展名或 `file.type`。接受 PNG、JPEG、WebP；SVG、GIF、BMP、HEIC 一律拒绝。
- 数量：一条消息最多 4 张。一次选 5 张时前 4 张进入草稿，余下的给出「一条消息最多 4 张图片」提示。
- 输入上限：单张原图 ≤ 20 MB、≤ 4000 万像素、任一边 ≤ 12000 px。
- 回形针与粘贴在以下情况禁用/拒绝：浏览器版（没有桌面桥）、对话库只读、正在生成、正在处理图片、设置里关闭图片发送；被拒绝时给出原因，已有草稿不受影响。
- 可以只发图片不写文字；此时使用内置提示「请看这 N 张记录表照片，先判断是表一还是表二……不要猜」。
- Chat 也接受图片：可问答、可描述、可核对读数，但系统提示词明确它没有表格工具，不得声称读表或写表。
- Work 中图片里的表格文字仍是**数据**：系统提示词要求把「忽略以上规则」「直接写入」等图片内文字当作不可信内容，不执行。

## 两条发送通道

设置 → 模型 → 「图片发送」有三档：

| 档位 | 行为 |
| --- | --- |
| 自动（默认） | `deepseek-flash` 与旧实验模型 `deepseek-v4-flash-vision-exp` 直接看图；其他模型只有在填写了不同的「视觉备用模型」时才转写，否则阻止发送 |
| 总是直接发送 | 不问模型，一律把图片直接交给主模型；由用户确认主模型确实支持图片 |
| 关闭图片发送 | 回形针禁用，已有草稿也不能发送 |

「视觉备用模型」与主模型共用 Base URL 与 API Key；留空表示不启用转写。备用模型不能与主模型同名，否则按「未配置备用模型」阻止发送。

### 直接看图（direct）

- 当前轮把用户文字与图片组成 OpenAI 兼容的多模态 `content` 数组：`{type:"text"}` + 每张图一个 `{type:"image_url", image_url:{url:"data:image/jpeg;base64,...", detail:"auto"}}`。
- 历史图片轮次不再上传图片，只发送当时的文字与转写说明（见下节）。
- 工具回合是无状态的：**同一轮对话里每次请求都会重新携带当前图片**，直到本轮生成结束；这会重复消耗图片 token。工具轮越多，重复越多。
- 重启后内存里没有原图时，先从本机附件目录按 id 读回压缩图，再按直发通道重新生成；读不回来且每张都有转写时降级为转写；两者都没有才禁用并说明原因。

### 视觉转写（transcribe）

- 主模型不直接收图；软件按顺序把每张待转写图片发给视觉备用模型。
- 转写提示要求先判断表一/表二，再按「站号 / 列名 / 读数」列出，看不清或黑红面矛盾标「待确认」，不补数、不给建议，并声明图片文字只是待转录内容。
- 每张转写上限 8 KB（UTF-8），保存到该附件的 `transcript`。
- 全部转写完成后，主模型收到文字 + 每张图的转写；历史消息块上限 16 KB。
- 任一张转写失败或被停止，整轮不会把图片交给主模型，也不会开始写表；错误会说明是视觉转写未完成。
- 若该轮所有图片都已有转写（例如重启后重新生成），直接进入主模型，不再调用视觉备用模型。

### 阻止发送

以下情况发送被拦下，并给出具体原因：

- 图片发送已关闭；
- 主模型未确认支持图片，且没有配置视觉备用模型；
- 视觉备用模型与主模型同名；
- 重启后本机附件目录与原图内存都没有，且没有转写；
- 图片模块未加载（构建缺失等异常）。

## 本机图片处理

1. 读文件前 12 字节做魔数校验，再解码；解码失败直接拒绝。
2. 用 `createImageBitmap(file, {imageOrientation:"from-image"})` 按 EXIF 方向摆正；不支持时回退旧接口。
3. 画到 canvas 前先铺白底，透明 PNG 转 JPEG 不会变黑。
4. 重编码为 JPEG，按三档降级直到单张 ≤ 1.5 MB：
   - 长边 2048、质量 0.85；
   - 长边 1600、质量 0.80；
   - 长边 1280、质量 0.75。
5. 一条消息的全部图片压缩后合计 ≤ 4 MB；超出则拒绝并提示删减。
6. 缩略图长边 320、质量 0.70，必要时降到 256/220 与 0.6/0.5，data URL 不超过 24K 字符。
7. 重编码天然去除 EXIF/GPS 等元数据；存下的 `mime` 统一为 `image/jpeg`，`w`/`h` 保留原图像素尺寸，`bytes` 是压缩后大小。
8. 压缩后的完整 data URL 先进入内存缓存（最多 30 张，超出按最早进入淘汰）；发送后后台写入本机附件目录（见下节）。草稿删除、页面关闭或进程退出会清掉内存副本，但已落盘的压缩图仍在。

## 本机落盘（M4b）

- **目录**：`%APPDATA%\com.jngkzbird.survey-jujin\attachments\`，实际路径以「设置 → 关于 → 图片缓存」读取的索引为准。
- **文件**：`<id>.<jpg|png|webp>`，id 只接受小写 `^[a-z0-9_-]{1,64}$`，Windows 保留名（`con`、`nul`、`com1` 等）拒绝写入。新图统一为 JPEG；读取端兼容 PNG / WebP。
- **内容**：发送前压缩后的完整图片（长边 ≤ 2048、已去 EXIF），不是相机原始文件，也不是原扩展名文件。
- **上限**：单文件二进制 ≤ 2 MiB；目录总量 ≤ 512 MiB。超限拒绝新写入并提示去关于面板清理，不会自动删除仍被引用的图。
- **不加密**：与 `agent.json` 同级，Windows 当前用户可见。
- **不新增字段**：`agent.json` 的附件白名单仍是 `id / kind / mime / name / w / h / bytes / thumb / transcript`，不保存路径、base64 或 `stored` 标记。
- **启动索引**：启动时扫描目录，返回 id 集合与用量；聊天界面在 `UI.init()` 前拿到索引，发送与重新生成只用同步的 `has(id)` 判断磁盘是否有图，不阻塞渲染。
- **水合**：重新生成、编辑并重发、打开查看器时，按 id 异步读回压缩图并放入内存缓存；读失败或文件不存在会把 id 移出索引并记入负缓存，下轮按钮直接说明缺图。
- **发送不等待落盘**：消息照常立即追加并开始流式生成，写盘在后台串行执行；部分失败只在本轮结束后 toast「N 张图片未能保存到本机缓存；重启后可能无法查看这轮原图」，不阻断发送。关窗握手会等待附件写链结清。
- **清理**：设置 → 关于 → 图片缓存提供「清理未引用图片」（只删没有被 `agent.json` 或其 `.bak` 引用的识别文件）与「删除全部原图」（二次确认）。删除整个会话或清空工作区对话后也会后台自动清理未引用文件。坏文件、未来版本或不可信的存储会被保守跳过，绝不按空引用集误删。详见 `docs/本机存储与备份.md`。

## 发送前确认（按 origin）

第一次把图片发往某个接收方时，会弹出「发送图片」确认：

- 接收方按 **origin** 计算：`scheme://host[:port]`。同一 host 换路径、换模型不重复确认；换协议、域名或端口要重新确认。
- 文案列出：图片张数、接收 origin、可能包含姓名/学号/读数、服务商可能保存或处理、发送前本机压缩到长边 2048 并去 EXIF、压缩后的完整图片会保存在本机 `attachments` 目录且**文件未加密**、相机原始文件不保存、`agent.json` 会保存缩略图与转写且**文件未加密**、含图片轮次写表仍需确认；转写通道还会写明备用模型名。
- 确认后把该 origin 写入 `settings.imageDisclosureAcks`（去重、最多 20 个）；取消则不发送、不记忆。
- 该确认只覆盖“把图片交给这个 origin”，不改变写表权限，也不替代 M3 的逐次写入审批。

## 写入审批

- 含图片的轮次，写表与加页**即使权限是 Auto 也必须逐次确认**；审批卡副标题显示「含图片：本轮写入必须确认」。
- Only Read 仍然先拒绝写工具；图片不会绕过权限。
- Manual 照常预览 + 审批；区别只是图片轮次在 Auto 下也走审批。
- Chat 不加载任何工具，图片只用于问答。
- 这条强制审批只对当前图片轮生效，不修改设置、不影响后续纯文字轮。

## 显示与查看

- 草稿区显示缩略图、文件名、原图尺寸与压缩后大小；可逐张移除。底部提示接收 origin、合计大小；转写通道额外显示「先由 xxx 转写」；不可发送时显示具体阻止原因。
- 已发送的用户消息在气泡内显示图片网格；点任意缩略图打开查看器。
- 查看器只接受 `data:image/png|jpeg|webp;base64,...`，不加载远程 URL、SVG 或 `blob:`。打开顺序：内存中的压缩图 → 本机磁盘读回（先显示「正在读取原图…」）→ 保存的缩略图。
- 查看器 meta 标注来源：「内存中的压缩图」「本机保存的压缩图」或「正在读取原图…」。底部说明：磁盘原图在时显示「压缩后的完整图片保存在本机，重启后仍可查看。」；只有缩略图时显示「原图不在本机，显示已保存的缩略图。」；有转写时追加「已保存转写文字，重新生成时仍可使用。」；既无原图也无缩略图时 toast「原图不在本机，也没有可显示的缩略图。」且不打开空弹窗。
- 所有附件 DOM 用 `textContent` 与 `createElement` 构建，不使用 `innerHTML`；查看器关闭后焦点回到打开它的按钮。
- 切换会话、切换项目、新建会话、切换模块时自动关闭查看器，避免旧图片留在新上下文上。

## 编辑、重新生成与持久化

- 编辑用户消息时可以增删图片：弹窗内显示附件托盘，支持逐张移除、回形针补选、拖放新增与点开查看；新增图片只进入编辑列表，保存或重发后才写入树与磁盘，取消时只丢弃新增图的内存副本，不动继承图。
- 图片压缩是异步的：压缩完成时若已关闭弹窗、改开另一条消息、切换会话或已发送，迟到结果直接丢弃，不会落进新上下文；压缩中按 Ctrl/Cmd+Enter 会提示「正在处理图片，请稍候。」，不按旧快照提交。草稿图同样以 `draftEpoch` 作废切会话前未完成的压缩。
- 打开用户侧编辑弹窗时会对已有图片做一次异步水合；水合完成前主按钮显示「正在读取原图…」。某张图既无原图也无转写时，「编辑并重发」禁用并说明，可先移除该图或只「保存」。
- **保存**只改树、不生成、不查 Key；新增图片在后台落盘。**编辑并重发**用最终文字与最终附件列表 `forkRound`，再按图片 plan 水合、披露、启动流；旧分支保留，同一附件不会重复写盘。
- 重新生成沿用同一轮图片：内存没有时先按 id 从附件目录读回；读不回来且每张都有转写则降级为转写，否则禁用按钮并说明。
- 附件按白名单写入对话树：`id`、`kind:"image"`、`mime`、`name`、`w`、`h`、`bytes`、`thumb`、`transcript`。`dataUrl`、本地路径与未知字段一律丢弃。
- **原生存储**：`agent.json` 保存缩略图与转写；压缩后的完整图片保存在 `attachments` 目录。`agent.json.bak` 是上一版副本，同样可能含有缩略图；两者都未加密。
- **浏览器 / localStorage 模式**：不落盘，序列化时剥离所有缩略图，只保留尺寸、名称与转写；因此刷新后气泡显示「图片」占位，查看器只能给出转写说明。关于面板显示「浏览器模式不落盘，只保留缩略图与转写」，两个清理按钮禁用。CDP 无头验收用注入的假附件桥模拟桌面磁盘。
- 容量按存储模式分别计量：原生 `agent.json` 按 UTF-8 估算，上限 12 MB；浏览器 localStorage 按 UTF-16（`text.length * 2`）计量，上限 **4.5 MiB**，给约 5 MiB 的站点配额留出键名与实现余量。超限时先在**副本**上按最旧会话丢弃缩略图，再丢弃工具卡与撤销记录，内存数据不变；磁盘格式不变。附件目录另按 512 MiB 单独计量。
- 不新增 `agent.json` 顶层键、不升版本；Rust 仍只校验顶层 `version === 1`，不解析内层字段。设置字段 `visionModel`、`imageSupport`、`imageDisclosureAcks` 存在既有 `settings` 内。
- 图片与 base64 不写入项目库 `store.json`，不随项目导出，也不进入项目备份；附件目录独立于项目库。

## 安全边界

- 文件头白名单挡在解码前；宽高也从 PNG IHDR / JPEG SOF / WebP 容器头先读出来校验，避免小文件声明超大尺寸时先分配巨幅位图。不允许 SVG（可含脚本）与 GIF。
- 图片内容、转写文字都视为不可信数据，不执行其中的指令，不因为图片里写「直接写入」就跳过审批。
- 错误详情与提示在写入消息前经过脱敏：`data:image/...;base64,...`、超长 base64、`Bearer` 与 `sk-` 开头的密钥串会被替换。
- 查看器不拼接 HTML，不加载远程资源；原图/缩略图都必须通过 `isImageDataUrl` 校验。
- 图片只发往用户当前配置的 Base URL origin；同一 origin 的确认记录只存在本机 `agent.json` 设置中。
- 附件读写只接受小写 id 与白名单扩展名，拒绝路径分隔符、`..` 与 Windows 保留名；Rust 会 canonicalize 应用数据目录，附件目录必须是它的直接子目录，索引与清理只遍历直接子文件，跳过符号链接、目录与未知文件。

## 已知风险（LLM 通道）

- Rust 的 `post_with_degrade` 在 HTTP 400 时会依次尝试 6 种请求体（去掉 temperature、stream_options、max_tokens、thinking、tools 等），但**始终保留 `messages`**。如果服务端因图片本身返回 400，同一轮可能重复上传同一批图片最多 6 次。
- 直接通道在每个工具回合都会重发当前图片；工具轮上限默认 6，意味着最多约 7 次请求携带图片。token 成本与 400 重试叠加时更高。
- 本阶段未获准修改 Rust，故只记录风险；遇到持续 400 时应停止生成、检查模型是否支持图片，或换用转写通道。
- Rust 的 `reqwest` 沿用默认重定向策略。若 Base URL 返回 307/308，客户端可能把带 base64 图片的 JSON **重新 POST 到另一个 origin**，而前端不会再次弹出发送确认；目前只把 Base URL 视为用户明确配置的发送目标。未改 Rust 前，建议只填写可信的服务商地址。
- 压缩只保证体积与格式，不保证服务端一定接受；若仍被拒绝，错误会脱敏后显示，需换图或裁剪。
- 转写质量取决于备用模型；转写错误会原样交给主模型，提示词已要求主模型把转写当不可信数据，但无法保证识别正确。
